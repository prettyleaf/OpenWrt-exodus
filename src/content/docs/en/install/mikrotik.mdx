On MikroTik Exodus runs in a container of RouterOS: it holds the Mihomo core, the [web UI](/en/usage/web-ui/) and the Zashboard dashboard, the same as on Keenetic. RouterOS sends the traffic of the chosen devices to the container, and the container keeps the rules of the router itself through the REST API.

:::caution
The MikroTik port is new, since 1.28.0. If something does not work, attach the report of `exodus debug` to the issue (see [Command line and files](#command-line-and-files)).
:::

## Requirements

- RouterOS **7.20** or newer: its containers have nftables with TPROXY.
- Architectures: `arm64`, `arm` (armv7) and `x86` (CHR included). MIPS and SMIPS routers have no containers.
- The `container` package and the container device mode.
- A disk formatted as **ext4** (USB, NVMe, SATA): the image takes about 100 MB. The internal flash works when there is enough of it, but wears out.
- About 100 MB of free RAM for the core.
- The REST API over the `www` (HTTP) or `www-ssl` service. If both are off, the installer turns `www` on for the address of the container only. The traffic between the router and the container does not leave the router.

## Preparation

<Steps>

1. **The container package.** Download *Extra packages* of your version and architecture from [mikrotik.com/download](https://mikrotik.com/download), upload `container-*.npk` to **Files** and reboot. Check with `/system package print`.

2. **The device mode.** Run in the terminal and confirm with the reset button (or a power cycle) within 5 minutes:

   ```text
   /system/device-mode/update container=yes
   ```

3. **The disk.** Format it as ext4 in **System → Disks**.

</Steps>

## Install & update

In the terminal of the router (WinBox → New Terminal, or SSH):

```text
/tool fetch url="https://raw.githubusercontent.com/prettyleaf/openwrt-exodus/mikrotik/install.rsc" dst-path=exodus-install.rsc; /import exodus-install.rsc
```

The installer:

- creates the veth `veth-exodus`: `172.31.255.2/30` for the container, `172.31.255.1` for the router; NAT for the container and an `input` rule, so the container reaches the REST API and the DNS of the router;
- creates the routing table `exodus`, the user and the group `exodus` for the REST API, the user logs in only from the address of the container;
- sets `registry-url` of `/container/config` to `https://ghcr.io` and pulls the image `prettyleaf/exodus-mikrotik:latest`;
- creates the container with the mount `<disk>/exodus/data` → `/opt/etc/exodus` and starts it, autostart with the router is on.

At the end it prints the password of the web UI. The address is `http://<router address>:9099/`: the container forwards the port from the addresses of the router on the interface list `LAN`. Directly: `http://172.31.255.2:9099/`.

**Updates.** The code of Exodus and the core are updated on the **Updates** page inside the running container, like on Keenetic. The image (Alpine and its packages) is updated by running the installer again: it recreates the container from the new image, settings, profiles and subscriptions in `<disk>/exodus/data` are kept.

**The core** (Mihomo Meta, Alpha or Prizrak-Core) is changed by the installer in the shell of the container:

```text
/container shell exodus cmd="sh /opt/share/exodus/install.sh"
```

### Installer options

Global variables set before the import:

```text
:global exodusDisk "usb1"; :global exodusPassword "secret"; /import exodus-install.rsc
```

| Variable | Default | Purpose |
| --- | --- | --- |
| `exodusDisk` | the first ext4 disk | the disk of the container: `usb1`, `nvme1`, `sata1` |
| `exodusPassword` | generated | the password of the web UI on the first install |
| `exodusLanList` | `LAN` | the interface list of the local network |
| `exodusNetwork` | `172.31.255` | the first three numbers of the /30 network of the container |
| `exodusIPv6` | `no` | `yes` gives the container `fd65:786f:6475::2/64` and NAT66, IPv6 is proxied then |
| `exodusImage` | `prettyleaf/exodus-mikrotik:latest` | the image on ghcr.io |
| `exodusFile` | — | an image file on the router instead of the registry, `github` downloads `exodus-mikrotik-<arch>.tar` of the [mikrotik-image](https://github.com/prettyleaf/openwrt-exodus/releases/tag/mikrotik-image) release |
| `exodusGhProxy` | — | [gh-proxy](/en/install/options/#if-github-is-blocked) for GitHub: the image file and the updates inside the container |

Without access to ghcr.io, download the image file through gh-proxy:

```text
:global exodusFile "github"; :global exodusGhProxy "https://example.com/ghproxy/TOKEN"; /import exodus-install.rsc
```

## Connection to RouterOS

The installer passes the REST API user to the container in `/container/envs`, the container writes it to its settings on every start. Check the connection in **Settings → RouterOS** → **Check**, it also holds the address of the REST API, the user, the password and the **interface list of the local network**: only the traffic from these interfaces goes to the container, the web UI is forwarded on them. The state of the connection is on the **Status** page too.

The devices to choose come from RouterOS: the DHCP leases and ARP, **segments** are the interfaces with an address (bridges, VLANs), **Wi-Fi networks** are the interfaces of the wifi and wireless packages and CAPsMAN; the clients of Wi-Fi networks are synced every 30 seconds.

## How it works

Every rule of the container in RouterOS has a comment starting with `exodus:`, the installer marks its part with `exodus setup`.

| Where | What |
| --- | --- |
| `mangle` prerouting → `exodus-pre` | TCP and UDP of the chosen devices get the routing mark `exodus`. The router itself, local networks and the direct networks of the settings go directly, Fake-IP always through the proxy, the DSCP marks work like on Keenetic |
| `mangle` output → `exodus-out` | the traffic of the router itself, when Traffic of the router is on |
| `nat` dstnat → `exodus-dns` | DNS of the chosen devices goes to the core |
| `filter` forward | two `accept` rules before fasttrack: fasttrack would skip the routing mark |
| `address-list` | `exodus-direct` for the direct networks, `exodus-ap` for the clients of the chosen Wi-Fi networks |
| a route in the table `exodus` | to the container, with `check-gateway=ping` |
| `netwatch` | turns the rules off when the container does not answer |
| `nat` dstnat | the web UI, the API of the core and the proxy port on the addresses of the router, while the container runs |

Inside the container nftables takes the traffic from the router to the TPROXY port of the core.

The rules are checked every 30 seconds and applied again when they are removed, changed, turned off, or another rule got above them. When the container does not answer, the route becomes inactive and netwatch turns the rules off: the devices go **directly, without the proxy**, until the container is back. A stop of the service removes the rules at once.

## Specifics of MikroTik

- TCP and UDP go through TPROXY by default. Redirect for TCP needs NAT of nftables in the kernel of RouterOS, Exodus logs it when there is none. TUN is not supported, TUN of the profile is turned off.
- Proxied packets stop in `mangle prerouting` at the rules of Exodus (`passthrough=no`): later rules of mangle prerouting, PCC or your own routing marks for example, do not see them.
- The `forward` chain of the router still applies to new proxied connections. A strict chain that drops everything except the WAN needs an `accept` for `out-interface=veth-exodus`.
- `router.lan` and other `.lan` and `.home.arpa` names are resolved by the router: its DNS has to allow remote requests (`/ip dns set allow-remote-requests=yes`, on in the default configuration).
- `registry-url` of `/container/config` is shared by all containers: after the installation other containers are pulled from ghcr.io too, until you set your registry back.
- The HWID is made from the serial number of the router (the software ID on CHR and x86) and stays the same after a reinstall.

## Command line and files

In the shell of the container, `/container shell exodus`:

```shell
exodus start | stop | restart | status
exodus routeros        # check the connection to the REST API of RouterOS
exodus apply           # apply the rules of the container and of RouterOS again
exodus debug           # report for an issue, server addresses and passwords are hidden
exodus passwd          # change the password of the web UI
```

Reset the password without the shell: `/container shell exodus cmd="exodus passwd"`. Logs of the container in RouterOS: `/log print where topics~"container"`, the logs of Exodus and the core are on the **Logs** page. Other commands are on the [Command line and files](/en/usage/cli/) page.

| Path in the container | Purpose |
| --- | --- |
| `/opt/etc/exodus/` | the mount `<disk>/exodus/data`: settings, profiles, subscriptions, the mixin file |
| `/opt/share/exodus/` | scripts and the web UI |
| `/opt/libexec/exodus/` | `mihomo` and `yq` |
| `/tmp/exodus/log/` | logs of the app, the core and the update |

## Uninstall

```text
/tool fetch url="https://raw.githubusercontent.com/prettyleaf/openwrt-exodus/mikrotik/uninstall.rsc" dst-path=exodus-uninstall.rsc; /import exodus-uninstall.rsc
```

The container, its rules, the user, the veth and the files are removed. `:global exodusKeepData yes` before the import keeps `<disk>/exodus/data`. The `registry-url` and the `www` service are left as they are.
